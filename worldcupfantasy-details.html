The Problem

My friends and family wanted to play fantasy football for the World Cup 2026. That sounds like a solved problem until you try to actually run it: standard fantasy platforms are built for a season, not a tournament where a 32-team knockout field halves every round, players get permanently eliminated mid-competition, and a per-nation ownership cap becomes mathematically impossible once only two countries are left standing.

Nobody sells that. So I built it, a full draft-and-manage fantasy app shaped around the tournament format, and ran it live for the group through the entire competition.

The Solution

Friends and family draft a 15-man squad of real World Cup players under a budget cap, set a starting XI plus a captain each round, and compete on a live-updating leaderboard as actual matches happen. Under the hood it's a Next.js 14 App Router app with 54 API routes, 25 pages, and 22 React components, backed by PostgreSQL on Neon through 16 Prisma models, with JWT auth (httpOnly cookies via jose) and bcrypt password hashing.

The Hard Problem: A Scoring Engine That Has to Be Exactly Right

The centerpiece is src/lib/live-scoring.ts, a full FPL-style points calculator: goals, assists, clean sheets, save and penalty-save math, card penalties, captain multipliers, and defensive-contribution thresholds modeled on real FPL's 2024-25 rule. It has to reconcile against a live, half-finished, occasionally-wrong data feed from API-Football while a match is in progress, and then be provably correct once the match ends. That's the whole game, if two managers see different points for the same player, the product is broken.

Points are position-dependent, not flat, and there's a tournament-specific twist: knockout matches carry a small bonus on top of the base goal value.

private calculateCleanSheetPoints(position: string, cleanSheet: boolean, minutes: number): number {
    // Must play 60+ minutes to get clean sheet points
    if (!cleanSheet || minutes < 60) return 0;

    switch (position) {
      case 'GK':  return SCORING.CLEAN_SHEET_GK;
      case 'DEF': return SCORING.CLEAN_SHEET_DEF;
      case 'MID': return SCORING.CLEAN_SHEET_MID;
      case 'FWD': return SCORING.CLEAN_SHEET_FWD;
      default:    return 0;
    }
}

Verification, Not Hope

To make that trustworthy I built three standalone test harnesses, wired into one npm test, no framework, just asserts and a pass/fail counter, deliberately dependency-light so it never breaks from an unrelated library update:

  • test-live-scoring.ts (932 lines) exercises every scoring rule combinatorially: appearance bands, position-specific goal and clean-sheet values, GK saves, defensive-contribution thresholds, red-card zeroing.
  • test-stage-advance.ts (481 lines) covers the stage-advance and elimination logic.
  • test-scoring.ts (270 lines) covers season-scoring aggregation.

Verification wasn't only synthetic either. Before trusting the pipeline against real tournament data, I ran it against a real live match happening during development and checked the computed points against what actually happened on the pitch.

Data Model & the Stage Abstraction

The interesting design decision in the 16-model schema is Stage: Groups → R32 → R16 → QF → SF → 3rd/Final, each carrying its own deadline, active flag, and completion state. A background "stage-advance" job locks squads at kickoff, banks points at full-time, and pushes the tournament to the next stage automatically.

Elimination is a first-class concept (Nation.isEliminated), which most fantasy football apps don't need but a knockout tournament fantasy app absolutely does, eliminated players get visually marked "OUT" and stop scoring, rather than just vanishing.

The Cap That Loosens as the Field Shrinks

Standard fantasy caps you at 3 players per country, fine with 32 teams, but by the Final only 2 nations exist, so a hard 3-cap makes fielding 11 starters mathematically impossible. The real function that fixes this:

// The field halves every knockout round (32→16→8→4→2). With the standard
// 3-per-nation cap and only 2 nations in the Final, you could own at most 6
// finalists but need 11 starters — an XI becomes impossible to field. So the
// cap loosens as the field shrinks:
//   • Default (groups → R16): 3 per nation.
//   • Quarter Finals (8 nations): 4 per nation.
//   • SF (4 nations): 5 per nation.
//   • Final round: no cap (Infinity) — a full XI from one finalist is
//     fillable, the "go all-in on the final" design intent, kept on purpose.
export function maxPerNationForStage(stageId: string | null | undefined): number {
  switch (stageId) {
    case 'QF': return 4;
    case 'SF': return 5;
    case 'F':  return Infinity;
    default:   return SQUAD.maxPerNation; // 3
  }
}

Deliberately enabling an "all-in on the finalist" strategy exactly when the format demands it.

Live Scoring Pipeline

A Vercel cron triggers a poller that, on each tick: pulls live fixtures from API-Football, feeds real-time stats through the scoring calculator, and writes per-player, per-match performance rows with an isLive flag. Points are only banked (finalized) once a match is actually full-time, with a self-healing re-score sweep, because API-Football sometimes marks a match FT before publishing final stats, which would otherwise freeze a match's points at an incomplete snapshot forever.

Three "safety sweep" jobs run alongside the main poller, unbanked-match healing, pending re-scores, and elimination sweeps, each independently idempotent so a cron retry or overlap never double-applies anything.

Admin/Ops: Where Trust Actually Gets Built

This is the part I'd highlight most in an interview, honestly. Every mutating admin action, manual point overrides, retroactive squad corrections, chip refunds, bug-driven data fixes, goes through an immutable AuditLog table with a revertedAt pointer, so nothing is ever silently edited; corrections are new rows that reference what they undo.

model AuditLog {
  id        String   @id @default(cuid())
  userId    String?
  action    String
  details   String
  ipAddress String?
  createdAt DateTime @default(now())

  // When this entry was reverted. Null = still in effect. UIs hide
  // reverted entries from default views so they don't clutter the
  // Adjustments list with +X/-X pairs.
  revertedAt        DateTime?
  // ID of the audit entry that reverted this one. Lets admins trace
  // cause/effect.
  revertedByAuditId String?

  @@index([userId])
  @@index([action])
  @@index([createdAt])
}

The Retroactive-Correction Pattern

The one I'm proudest of. When a real bug or a legitimate "I meant to make this transfer 20 minutes ago" request comes in mid-tournament, I don't want to spend a free transfer or apply a hit for something that's genuinely the app's fault or an owner-authorized backdate. So I built a repeatable pattern: a direct squad-row swap (same slot, same starting/captain state) with bank and value adjusted by the exact price delta so bank + value stays conserved to the penny, wrapped in a transaction with the audit row, guarded by sanity checks, position match, "not already owned", "bank can't go negative", that throw before touching the database if anything's off.

if (outPlayer.position !== inPlayer.position) {
  console.log('POSITION MISMATCH — aborting'); return;
}
const alreadyOwns = await prisma.squadPlayer.findFirst({
  where: { teamId: team.id, playerId: inPlayer.id },
});
if (alreadyOwns) { console.log('already owned — aborting'); return; }

const netDelta = round(inPlayer.currentPrice - squadRow.purchasePrice);

await prisma.squadPlayer.update({
  where: { id: squadRow.id },
  data: { playerId: inPlayer.id, purchasePrice: inPlayer.currentPrice },
});
await prisma.team.update({
  where: { id: team.id },
  data: {
    bankBalance: round(team.bankBalance - netDelta),
    teamValue: round(team.teamValue + netDelta),
  },
});
await prisma.auditLog.create({ data: { action: 'ADMIN_RETROACTIVE_SQUAD_CORRECTION', details: '...' } });

💡 I used this exact pattern live, mid-conversation, correcting multiple teams' squads during the Final and then fully reversing two of them without leaving residue. The audit trail shows both directions cleanly, which is the entire point of building it this way instead of hand-editing rows.

The 221 one-off scripts I've accumulated over the season, check-, audit-, fix- scripts for specific incidents, checking a specific player's live minutes lagging the API, auditing group-stage banking sums, verifying penalty-save scoring after a rule change, are the unglamorous truth of running this live. They default to dry-run when they mutate data, because a fantasy app's database is basically money and reputation with your friends.

Frontend Engineering Worth Calling Out

  • kit.tsx: a from-scratch SVG jersey renderer, real per-nation stripe/hoop/sash patterns, gradient shading for a pseudo-3D look, captain/vice armband badges, a live-points pill, all parameterized so roughly 200 nations render correctly from just two kit colors and a country code. A PlayerFace component overlays real headshots on the same kit-colored frame and gracefully falls back to the pure-SVG shirt if the photo 404s.
  • The /table mobile interaction: a finger-tracked drag-to-reveal column expansion, collapsed "# Club P Pts" opens W/D/L/GD by dragging, half-open is a valid resting state, driven entirely by a CSS custom property written directly in the touch handler (no React re-render per pixel of drag, transitions suppressed during drag via a class toggle). It went through four rejected approaches first: a real <table> with sticky columns (CSS max-width doesn't clamp table cells), native horizontal scroll (felt "patchy" with no snap state), and a discrete toggle-on-threshold, each rejected for a specific, memorable failure mode before landing on the drag-driven version.
  • Auth-gated route groups with JWT session refresh, a splash-screen remover, and an iOS PWA install prompt for the "add to home screen" flow friends actually use on their phones.

War Stories: Real Bugs, Real Fixes

  • Float-drift in banked points. Repeated bank/value arithmetic across many transfers slowly desynced fractional pennies from the true squad value. Fixed with consistent rounding at each mutation point rather than only at display time.
  • Non-additive mercy-transfer bug. The QF→SF stage transition computed free-transfer "mercy" (extra transfers for teams that lost players to elimination) using a formula that replaced rather than added to existing free transfers, silently costing teams transfers they'd already banked. Caught, fixed, and, critically, retroactively re-applied to every affected team via an audit-logged sweep script across roughly 25 teams, rather than just fixing it forward and leaving already-wronged teams shorted.
  • Ghost-state bug in the lineup builder (found and fixed in the sister La Liga codebase, same root architecture): after a transfer, a child component kept its stale starting player-ID set because it wasn't remounted, so a transferred-out player's ID lingered as a "ghost", inflating the starting-XI count to 12 and disabling Save with a completely unrelated error message because the disabled-reason logic fell through every specific branch to a generic fallback. Root-caused by tracing the exact state transition, not just patching the symptom.
  • Budget double-counting in transfer validation. It compared the current market value of the entire squad against just the bank plus one player's sale price, two numbers that were never comparable, producing wildly wrong "exceeds budget" errors on completely normal transfers. Dead code path nobody had hit until the La Liga fork surfaced it.

Proof the Architecture Generalizes: The La Liga Fork

Rather than describe the architecture in the abstract, I fork-forwarded the entire app into a second, real product: a season-long, 38-gameweek La Liga fantasy app reusing about 80% of the World Cup codebase almost unchanged, same scoring engine (re-verified 75/75 against the new rule set), same gameweek/lock/live-update pipeline, same auth and league system.

The port required renaming the tournament-specific concepts, Nation → Club, Stage → Gameweek, and dropping the elimination/bracket logic, but proved the core engine, banking model, and admin-correction pattern weren't tournament-specific hacks, they're a reusable fantasy-sports platform. That fork syncs against real 2026-27 La Liga data via API-Football Pro (20 clubs, 552 real players, 380 real fixtures across 38 real gameweeks with real kickoff-derived deadlines), and its scoring engine was checked against a genuinely live match (LA Galaxy 0-3 LAFC) during development the same way the original was.

What I Learned

  • An audit trail is worth more than being right the first time. Bugs happen, especially against a live external data feed. What matters is being able to prove exactly what broke, when, and how it was made right, instead of hand-waving "yeah I fixed it."
  • Fix forward and fix backward. The mercy-transfer bug taught me that patching the bug going forward isn't enough if it already wronged real users, the retroactive sweep across every affected team was the actual fix.
  • A second real product is the best architecture review. Forking to La Liga surfaced dead code paths and design assumptions no amount of self-review would have caught, because a second consumer of the same code doesn't share my blind spots.
