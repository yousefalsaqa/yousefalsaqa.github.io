Document Automation

A PeopleSoft document-attachment bot (peoplesoft_attach_bot.py) that watches a folder for scanned admission documents and attaches each one to the right student record, unattended, batch after batch. Started as a personal script during the Admission Coordinator role, now the office's main way of attaching documents, 20,000 to 30,000 documents in a single admission cycle.

Role Sole Developer
Timeline Jan 2026 to Present
Stack Python, Selenium WebDriver, pandas
Status In daily, office-wide use

The Problem

Scanned admission documents, transcripts, IB and GCSE final results, English test scores, and more, land in a shared folder and need to be attached to the right student's record in PeopleSoft's Campus Solutions "General Materials" component. Manually, that's open a document, find the student ID, search PeopleSoft, navigate to their record, upload, repeat, hundreds of times a day.

The Solution: a Filename Protocol as the Interface

The bot's entire interface is a filename convention: DOCCODE-YYYYMMDD-STAFFID-STUDENTID.pdf. Every document that reaches the folder gets parsed by parseFileName(), which strictly validates that pattern before the bot touches PeopleSoft at all. A malformed filename fails fast and cheap, before a browser session ever opens, instead of failing halfway through one.

There's no GUI. It runs from a terminal and is designed to be handed off to non-programmer admissions staff, there's a dedicated SETUP GUIDE.txt for that handoff.

A Folder-Based State Machine

No database. Just folders and a CSV:

incoming/   →  processed/   (success)
            →  error/       (failure)

every outcome appended to ps_attachment_log.csv

That log is the full audit trail: who attached what, when, and why anything failed, without needing a database.

Fighting PeopleSoft's Frame Structure

PeopleSoft renders all of its real content inside nested iframes (ptifrmtgtframe → TargetContent → main), and every PeopleSoft-triggered page refresh kicks the driver back out to the top frame. switchToIframeIfPresent() re-enters the correct frame after every single refresh before the next interaction can happen.

On top of that, each file gets up to maxRetries attempts. A failed attempt reports back whether the browser landed in a confirmed-good state (sitting on the search page) or an unknown one, and the next file only pays for a full page reload if recovery is actually needed, otherwise it reuses the page that's already loaded. That distinction is what made the biggest performance fix (below) possible to find and to trust.

Three Bugs Worth Walking Through

The Slowdown: Root-Causing Instead of Guessing

The bot was intermittently "insanely slow" compared to using PeopleSoft by hand. Instead of guessing at a fix, I diagnosed it by systematically eliminating variables using Chrome DevTools network timing: ruled out client-side rendering, ruled out bot-detection or WAF fingerprinting (tested by stripping Selenium's automation signature and comparing), ruled out CPU or resource contention (verified in Task Manager), one variable at a time. The actual cause: a full browser-profile reload was firing on every single file instead of once per batch, needlessly re-paying PeopleSoft's expensive portal-chrome initialization (nav bar, browser-check iScripts) for every student instead of once.

The Race Condition That Reload Fix Uncovered

PeopleSoft assigns an incrementing ID to its file-upload modal iframe (ptModFrame_0, _1, _2, ...) that only resets on a full page reload. Once the redundant-reload fix above stopped reloading between files, hardcoded exact-ID matching started intermittently failing, because the counter had moved past whatever ID the code expected. Fixed by matching iframes by ID prefix instead of an exact value, so it works no matter where the counter currently sits, a small but real lesson in not hardcoding assumptions about server-generated IDs.

The Save-Confirmation Race

The bot was clicking "Return to Search" before PeopleSoft's save had actually finished server-side, which triggered a spurious "unsaved changes" popup. Fixed by waiting on PeopleSoft's own asynchronous status indicator, an aria-live region that flips to "Saved", instead of a fixed sleep, and specifically waiting for it inside the correct iframe, since PeopleSoft's transactional pages keep their own internal document context separate from the outer portal chrome.

What I Learned

  • Eliminate variables systematically, don't guess. The slowdown looked like a dozen possible causes. Ruling each one out methodically with real measurements (DevTools timing, Task Manager, stripped automation signatures) found the actual cause, a redundant reload, in a way guessing never would have.
  • Don't hardcode assumptions about server-generated IDs. The modal-iframe race only existed because the code assumed an exact ID instead of a pattern. Fixing the reload bug exposed it immediately.
  • Wait on the system's own state, not a timer. Fixed sleeps are guesses about timing that will eventually be wrong. Waiting on PeopleSoft's actual save-status indicator is correct regardless of how fast or slow that particular save happens to be.
