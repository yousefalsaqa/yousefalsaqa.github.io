Admission Coordinator Assistant

A Tkinter desktop app that drives five simultaneous, independent PeopleSoft browser sessions behind one Start / Next / Skip workflow. The evaluator reads the documents and types one number. The system handles everything around that judgment.

Role Sole Developer
Timeline Jan 2026 – Present
Stack Python, Tkinter/ttk, Selenium (5 concurrent sessions)
Status In daily use

The original workflow

Reviewing an admission file is not one job. It is about a dozen. Before this tool existed, the evaluator opened a folder of documents, read the transcript, calculated a score off the applicant's grades, then walked that result through several separate PeopleSoft components by hand: General Materials to review and sign off each document, Application Evaluation to enter an evaluation code and the score, Checklist to work through status changes, and, for certain applicants, OUAC Application and Maintain Application to update the admit basis. Then the next student in the queue, from the top.

Each of those components lives on its own page with its own student search. Same student, searched again and again, one component at a time.

Sources of friction

The actual judgment, reading the transcript and figuring out the score, is a small fraction of the work. The rest is mechanical navigation, and three things make that navigation worse than it sounds.

PeopleSoft has no API. Everything happens through the browser: page loads, search forms, grid pagination, modal dialogs. There is no shortcut underneath.

The scoring rules genuinely differ by curriculum. These are not small variations on one formula:

Curriculum Score calculation
IB Subject scores are summed
CBSE / ISC Subject scores are averaged
GCSE / A-Level Grades pass through a 1-9 to 1-6 conversion table first

Admit basis is a lookup problem. Setting it correctly means finding the right code in a roughly 90-entry Ontario/OUAC admit-basis table, per applicant, on top of per-program subject and score requirements.

Volume and repetition

None of this would matter for ten students. It matters because the same chain repeats across hundreds of students in a cycle, and every repetition is identical except for the one moment of judgment in the middle. The original IB-only version of this tool alone carried about 1,200 applications. That is roughly 1,200 runs of the same navigation sequence that no longer happened by hand.

Process map

The transformation is easiest to see side by side. The manual version is a serial chain the evaluator walks personally. The automated version reorganizes the same steps into a pipeline: the human moment stays exactly where it was, and everything around it fans out to five browser sessions working in parallel.

Automation strategy: five sessions, real threads

The tool drives five simultaneous, independent PeopleSoft browser sessions, each with its own persistent Chrome profile. Three launch at startup, one per core component: General Materials for document review and sign-off, Application Evaluation for evaluation code and score entry, and Checklist for status changes. The remaining pair, OUAC Application and Maintain Application for admit-basis updates, is opt-in and launched on demand rather than at startup, to save resources when it is not needed.

Loading a student is fan-out, fan-in concurrency. Clicking "process student" spins up a worker thread per active browser (_process_student_thread), and each thread independently searches for and loads that student in its own PeopleSoft session. All threads are joined before the UI updates, so the interface never reflects a half-loaded state. That is genuine parallel automation, not just background work moved off the UI thread. Every cross-thread UI update is funneled through root.after(0, ...) so it lands correctly on Tk's single UI thread.

Rules as configuration, not code paths

A central CURRICULUMS config table drives which PeopleSoft fields to write to and how to calculate a score. IB summing, CBSE/ISC averaging, and the GCSE/A-Level 1-9 to 1-6 conversion table all live there, alongside the roughly 90-entry OUAC admit-basis table and per-program subject and score requirements. A hardcoded IB-only version would never have generalized; a config table did.

Interface design: read, type one number

The whole interface reduces to Start / Next / Skip. The evaluator's job is to read the documents on screen and type one number, the score. Everything else, the searches, the field entry, the sign-offs, the checklist changes, happens underneath.

The one place the interface adapts is the on-screen calculator widget, which reconfigures its own button layout depending on which curriculum is active. It is a different calculator for IB than for GCSE, without being a different screen.

Exception handling: the allow-list and the human pause

PeopleSoft throws popups. Some are routine and safe to dismiss; some mean something is genuinely wrong. A recover_to_search() routine auto-dismisses known-safe alert dialogs from an explicit allow-list, and for anything unrecognized it does not guess. It pauses, for up to two minutes, and waits for a human to step in.

That is a deliberate fail-safe boundary between what the automation is allowed to decide on its own and what it hands back to a person. Building a boundary is more honest than pretending to handle every possible PeopleSoft dialog automatically.

Reliability

Daily use is a different standard from a working demo, and most of what earns it is unglamorous. The recovery routine gives every session a known path back to the search screen instead of an undefined state. Joined worker threads mean the UI only ever shows a fully loaded student. And gm_goto_row() computes the cheapest way to reach a specific row in a document grid, stepping through Prev/Next versus jumping to First/Last and walking back, a small shortest-path calculation that cuts down on PeopleSoft round-trips, which are both the slowest and the most failure-prone part of any browser automation.

Adoption

This started as a personal, IB-only tool built during the Admission Coordinator role, used by the person who wrote it. It earned its place by being reliable at that one curriculum, about 1,200 applications' worth. During the Business Analyst role it grew into an internal system covering multiple curricula behind a mode-picker: an evaluator picks a curriculum family and gets the right tool.

The largest addition is ps_cegep_eval.py (~1,450 lines), a second, comparably complex dashboard purpose-built for Quebec CEGEP evaluations, with its own course-categorization and grade-average logic. CEGEP transcripts do not map onto the IB/CBSE/GCSE model at all, so instead of forcing them into the config table, they got a sibling tool launched from the same entry point.

Operational outcome

~5,800 Lines: dashboard + CEGEP variant + shared helpers
5 Parallel PeopleSoft browser sessions
~1,200 Applications processed by the original IB-only version
Daily Usage frequency

What used to be a manual, multi-page-per-student PeopleSoft workflow is now one click and five browsers working in parallel, across an entire admissions cycle's applicant roster and multiple curricula. The evaluator's attention goes where it is actually needed: the transcript and the score.

Software does not need to be glamorous to matter. The judgment stayed human. Everything mechanical around it went away.

Maintenance

  • New curriculum, config entry. Because field mapping and score calculation live in the CURRICULUMS table, extending the tool usually means adding configuration, not rewriting logic.
  • When the model does not fit, do not force it. CEGEP got its own ~1,450-line evaluator behind the shared mode-picker rather than a pile of special cases inside the main one.
  • The allow-list grows one verified dialog at a time. A popup only becomes auto-dismissable once it is understood. Until then, it pauses for a human. That boundary is what makes the tool safe to keep extending.
