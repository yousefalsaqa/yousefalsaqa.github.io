Automatic Recruiter Coordinator

A report generator (school_application_analysis.py) that turns a raw admissions export into a formatted feeder-school and regional-conversion report for one country or region at a time, fuzzy-matching school names, decoding denial reasons, and flagging high-volume, low-yield schools as recruiting targets. Named for what it actually does: the analysis a recruiter would spend a day doing by hand, automatically, coordinated across every region.

Role Sole Developer
Timeline May 2025 to Jan 2026
Stack Python, pandas, rapidfuzz, Tkinter, openpyxl
Status In use by team

The Problem

Working as a recruitment rep at Queen's, I had access to years of application data, every applicant who had ever applied, regardless of whether they got in. But it all came as a raw "AC Report" export. Every question, "which schools send us the most applicants and how many of them actually enroll?", meant manual pivoting, hand-deduplicating school name spelling variants, and cross-referencing denial codes by hand. A day of work for one report.

The Solution

A command-line tool, with a Tkinter GUI wrapper (school_application_analysis_gui.py) for non-technical use, that turns the raw export into a formatted Excel report and a set of charts for one country or region at a time. Nearly all of the logic sits in a single function, analyse(), about 1,300 lines on its own.

Fuzzy-Matching School Names

Feeder-school data is never clean, "Upper Canada College" and "UPPER CANADA COLLEGE" and a typo'd variant are the same school, but a straight string match won't see it. The tool uses rapidfuzz token-sort-ratio with a 90% match threshold to collapse those variants into one canonical school automatically.

Regions, Not Just Countries

Countries get normalized into regions through a hand-built lookup table, so "MENA" or "USA" can be run as a single filter instead of manually selecting every country that belongs to it.

Dual-Level Outcomes, With a Priority Rule

Outcomes get computed at both the per-application and the per-student level, with an explicit priority rule: Offer > Pending > Deny > Other. That means a student denied by one program but offered by another correctly counts as an offer, not a denial, which fixes a subtle double-counting error that's genuinely easy to make doing this by hand.

Denial Codes and Data-Quality Checks

Denial reason codes get decoded against a 34-entry dictionary instead of staying as raw codes in a spreadsheet, and the tool flags data-quality impossibilities on its own, like enrollments exceeding offers, and surfaces "high-volume, low-yield" feeder schools as relationship-building targets worth a second look.

Output

One Excel workbook with every table, plus two multi-panel PNG dashboards, dropped straight into a report someone's already writing.

Worth Knowing

The project's README.md describes a much bigger statistical framework, scikit-learn models, YAML-driven configs, than this script actually uses. That README documents a different, more aspirational system, not the one that's actually running. Worth being upfront about: the tool that ships is the one described above, a fuzzy-matched report generator, not a machine-learning pipeline.

By the Numbers

170K Applications analyzed
5 Years of data
90% Fuzzy-match threshold for school names
34 Denial reason codes decoded

What I Learned

  • Real-world text data is never clean. Fuzzy matching school names wasn't optional polish, it was the difference between a usable feeder-school ranking and a list fragmented across dozens of near-duplicate spellings.
  • An explicit priority rule beats an implicit assumption. Deciding Offer > Pending > Deny > Other up front, and applying it consistently, is what prevents a student's real outcome from getting miscounted when they touch multiple programs.
  • Document what's actually running, not what you meant to build. Leaving the README's bigger aspirational framework unreconciled with the real script would have been misleading. Better to be direct about which one ships.
