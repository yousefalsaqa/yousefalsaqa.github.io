Method

Operating principles

01

Integrate before you optimize

Individual components usually work. The seams between them are where projects die.

Seen in: Terrabot's five-subsystem integration AutoDrive CAN timing CAST, three subsystems made invisible

02

Design for the person using it

A technically correct system still fails if its workflow confuses the person operating it.

Seen in: ACA's one-number interface A filename protocol handed to non-programmers CAST, built for nursing students

03

Build for the second use

A prototype proves the idea. Documentation and reliability are what make it survive contact with someone else.

Seen in: World Cup Fantasy forked to La Liga A Commerce-only dashboard made config-driven Ops scripts that default to dry-run

About

Two kinds of system, one instinct

Half my work is physical: a manikin that has to respond correctly while a nursing student is holding it, a vehicle that has to make a decision every 100 milliseconds, a rover that has to survive its own drivetrain. The other half is software with the same problem — a scoring engine running during a live match, an agent holding state across weeks, a game where the physics is the mechanic.

They are the same job. Find where the thing will come apart, and get there first. I graduated from Queen's in mechatronics and robotics engineering in 2025, and I've been building since well before that.

Have a system that has to hold?

Robotics, automation, embedded work, or anything where software meets something physical.
